API GUIDE — FRONTEND INTEGRATION

HOW REQUESTS WORK
React pages call functions in frontend/src/services/.
Those functions use apiRequest() in frontend/src/services/api.js.
The helper adds the backend address, JSON headers, and login token.
The older api() wrapper in frontend/src/api/client.js uses the same helper.

FRONTEND ADDRESS SETTINGS
VITE_API_URL may include /api at the end, or just the server address.
If it is unset, /api requests use the Vite proxy.

Normal local backend:
  VITE_API_URL=http://localhost:5000/api

Private practice backend:
  VITE_API_URL=http://127.0.0.1:5013/api
  VITE_DEMO_AUTH=false

For a deployed frontend, use the deployed backend address.
Restart Vite after changing its environment settings.
Set the intended address before building because Vite includes it in the build.

Example service helper:
  import { apiRequest } from './api';

  export function getServices() {
    return apiRequest('/services').then((data) => data.services);
  }

LOGIN AND PERMISSIONS
POST /api/auth/register creates a customer account without a token.
POST /api/auth/login returns access_token and user.
AuthContext saves the token in localStorage under token.
The shared helper sends Authorization: Bearer <token>.
Normal login tokens use main's one-hour duration.

A protected 401 clears an expired login.
A wrong login password shows its normal error.
Admin routes enforce the admin role on the backend.
Both API import paths use the auth:session-expired notification.

POST /api/auth/logout lets the frontend remove its saved token.
This does not revoke an already-issued token on the server.
GET /api/auth/me restores the signed-in user's details.
GET and PATCH /api/users/me load and save the user's profile.

PASSWORD CHANGES AND RESET
POST /api/auth/change-password requires a signed-in user.
It accepts current_password and new_password.
An incorrect current password returns 400 and keeps the user signed in.

POST /api/auth/forgot-password sends a reset email for an active account.
POST /api/auth/reset-password accepts token and password.
Reset links expire after 30 minutes.
Changing a password invalidates earlier reset links for that account.
Request a new email when testing the updated reset-link format.

ERROR HANDLING
200/201: success.
204: success with no response body.
400: invalid input; show error and details when provided.
401: invalid or expired login.
403: account or role is not permitted.
404: record not found.
409: duplicate or conflicting update.
500/502/503: server or external-service problem; allow a retry.

Never display a failed save as successful.
Do not replace failed live requests with sample account data.

An empty live list or request failure is shown explicitly.

Orders:
Customer orders/invoices and admin order management.

Catalog:
Public products/options and admin product management.

Hair specifications:
Customer saved choices and fitted-system reordering.

Appointments:
Setmore booking links, imported bookings, admin tracking,
and links between received orders and appointments.

See registered backend routes and frontend service helpers
for exact paths, request fields, and response shapes.

DASHBOARD AND SETTINGS
In live mode the owner dashboard reads appointment, order,
inventory-report, and sales-report APIs.
Dashboard dates follow Central Time.
It reads the last saved Calendar sync.
Refreshing the dashboard does not contact Setmore.

Customer orders and supplier purchases have separate navigation links.
Admin Settings is informational.
It does not save notification preferences.

SETMORE
Customers book, reschedule, and cancel through Setmore.
A saved card or deposit is not required to book.
The admin Calendar imports bookings into the application's database.
No-show tracking does not automatically charge a fee.

Keep SETMORE_API_BASE_URL and SETMORE_REFRESH_TOKEN on the backend.
The private launcher's --mock-setmore flag selects simulated responses.
Omit that flag to test the real read-only import.

The Setmore reader returns one provider page at a time.
Appointment logic handles pagination and saving.
Keep those two parts matched when updating the implementation.

Main's standalone sync_services_from_setmore helper remains available.
It defaults to a dry run.

EMAIL
Keep EMAIL_FROM and EMAIL_APP_PASSWORD on the backend.
Use CONTACT_DELIVERY_METHOD=smtp for SMTP Contact delivery.
CONTACT_TO_EMAIL selects the contact inbox.
EMAIL_FROM is the fallback contact inbox.
CLIENT_URL must match the frontend address used in reset-email links.
The public business email may differ from the delivery inbox.

STRIPE
Use matching sandbox keys for class testing.
Only VITE_STRIPE_PUBLISHABLE_KEY belongs on the frontend.
STRIPE_SECRET_KEY and STRIPE_WEBHOOK_SECRET belong on the backend.

Card numbers and CVC values go to Stripe.
Do not store them in the application's database.

Forward the required payment and saved-card events to:
  /api/webhooks/stripe

Confirm the saved payment status after Stripe confirmation.
The webhook may arrive shortly afterward.

DATABASE AND DEMO HANDOFF
Normal backend startup uses backend/run.py and the configured database.

The database owner must review the required setup scripts:
  backend/create_catalog_tables.py
  backend/create_hair_specification_table.py
  backend/create_purchases_table.py
  backend/upgrade_appointments.py

These scripts require --apply.
Coordinate with the database owner before using a shared database.
Creating a table does not upgrade an existing table's columns.

backend/run_inventory_local.py uses a private practice database.
Its example accounts and fixed test secrets are local testing aids.
Keep this launcher out of the source commit unless the team chooses
to include it as a separate demo tool.
Do not copy its accounts or secrets into normal startup.

FINAL CHECKS
Use npm ci in frontend to install package-lock.json versions.
Run npm run lint and npm run build.
Test browser workflows against the intended backend.

Keep these out of the source commit:
  .env files
  private databases
  virtual environments
  node_modules
  generated dist files

Review the final changes against the team's chosen PR target.
Local testing does not replace testing the final combined branch.

TROUBLESHOOTING
Connection refused:
Check Flask is running on the configured port.

CORS error:
Backend CLIENT_URL must match the frontend origin exactly.

Database error:
Check access and required schema with the database owner.

Old settings:
Restart Flask or Vite after changing its environment.

Calendar Details:
The appointment details panel appears below the appointment list.

Do not share secret keys or password-reset links in logs or screenshots.
