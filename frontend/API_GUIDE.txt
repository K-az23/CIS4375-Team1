API GUIDE (FOR FRONTEND DEVELOPERS)

PURPOSE
How the React frontend connects to the Flask backend: where requests
go, what comes back, and how to set up your computer to test it.
For how the backend itself is built, see backend/README.txt.

HOW IT FITS TOGETHER
----------------------------------------------------------------------
React page or component
  -> function in frontend/src/services/  (the only place that calls
                                          the API; pages never call
                                          fetch directly)
  -> Flask backend at VITE_API_URL
  -> MySQL database (or Setmore)
  -> JSON back to React

The frontend never talks to the database or Setmore directly.

WHERE TO CONNECT
----------------------------------------------------------------------
In development the frontend calls relative paths like /api/services,
and Vite's proxy (frontend/vite.config.js) forwards anything under
/api to the Flask backend on http://127.0.0.1:5000. So:
  frontend/.env:  VITE_API_URL=          (leave blank)
Only set VITE_API_URL when the backend is hosted somewhere else.

Every request goes through api() in frontend/src/api/client.js, which
adds the login token, turns the backend's error into one readable
message, and logs the user out when the token expires.

Example:
  import { api } from '../../api/client';
  api('/api/services').then((data) => setServices(data.services));

Shared formatting (dates, statuses, phones, order specs) lives in
frontend/src/api/format.js so every page labels things the same way.

RUNNING THE BACKEND LOCALLY
----------------------------------------------------------------------
To test against real data, the backend must be running on your
computer at the same time as the frontend:

1. Follow FIRST-TIME SETUP in backend/README.txt (Python, venv,
   packages). You need a backend/.env with database credentials
   (ask the database manager privately, never in the group chat)
   and your IP added to the RDS security group.
2. Open two terminals:
     Terminal 1 (backend):   cd backend
                             venv\Scripts\Activate.ps1
                             python run.py
     Terminal 2 (frontend):  cd frontend
                             npm run dev
3. Check the backend works: http://localhost:5000/api/health
   should show {"status": "ok"}.

REQUEST AND RESPONSE RULES
----------------------------------------------------------------------
Full details for every endpoint (inputs, example responses, errors,
and rules) are in CIS4375_API_Workbook.xlsx:
  - Priority Overview: every endpoint and its status. Only connect
    to endpoints marked Done.
  - Conventions: error format, status codes, dates, money.
  - Object Shapes: every field and its type.
  - One sheet per area (Services, Auth, Users, ...).

The short version:
  - Everything is JSON.
  - One record comes back under a singular key:  { "service": {...} }
  - A list comes back under a plural key:        { "services": [...] }
  - Errors always look like:                     { "error": "message" }
    so you can show the message to the user.
  - Money and quantities are numbers (120.0), not strings.
  - Timestamps (placed_at, charged_at, created_at) are UTC without a
    "Z": "2026-11-12T06:52:51". format.js adds the Z before showing them.
  - Appointment times are the salon's wall-clock time from Setmore and
    are shown as stored (see APPOINTMENTS below).
  - Field names are snake_case: service_name, duration_minutes.

STATUS CODES TO HANDLE
----------------------------------------------------------------------
  200 / 201  Success
  400        Invalid input; show the error (and "details" if present)
  401        Not logged in or login expired; send the user to Login
  403        Wrong role; show a "no permission" message
  404        Not found
  409        Duplicate (e.g. email already registered)
  500        Server problem; show a generic "try again" message

LOGIN
----------------------------------------------------------------------
Login uses a token (JWT) sent with every request.

1. POST /api/auth/login with {"email", "password"} returns
   { "access_token": "...", "user": {...} }
2. Save access_token in localStorage under "token".
   (AuthContext must read data.access_token, not data.token.)
3. client.js adds "Authorization: Bearer <token>" to every request.
4. Tokens expire after 30 minutes. A 401 means: send the user to Login.
5. POST /api/auth/register returns { "user": {...} } but NO token, so
   log the user in right after registering.

Admin routes check the role on the server; a customer gets 403.

TROUBLESHOOTING
----------------------------------------------------------------------
CORS error in the browser console
  The frontend is calling the backend directly instead of through the
  Vite proxy. Make sure VITE_API_URL in frontend/.env is blank and
  restart npm run dev.

"Failed to fetch" / connection refused
  The backend isn't running. Start it (Terminal 1 above).

/api/health works but /api/health/db shows an error
  The backend can't reach the database. Check backend/.env and that
  your current IP is in the RDS security group (home and campus IPs
  are different, so you may need both).

Changes to .env not taking effect
  Restart the server. Both Vite and Flask only read .env at startup.

AVAILABLE ENDPOINTS
----------------------------------------------------------------------
Only endpoints listed here are built and ready to connect.

GET /api/services                         SVC-01  List active services (public)
GET /api/services/<service_id>            SVC-02  Get one active service (public)
                                                  404 if missing or inactive
GET /api/admin/services                   SVC-03  List services with admin fields (admin)
                                                  ?include_inactive=true to include inactive
POST /api/admin/services                  SVC-04  Create a service (admin)
                                                  Required: service_name, duration_minutes, price
                                                  Optional: description, setmore_service_id
PATCH /api/admin/services/<service_id>    SVC-05  Edit a service (admin)
                                                  Send only the fields being changed:
                                                  service_name, description, duration_minutes,
                                                  price, setmore_service_id
                                                  {"is_active": true} reactivates
DELETE /api/admin/services/<service_id>   SVC-06  Deactivate a service (admin)
                                                  Does not delete; hides it from customers

service_id is a number (e.g. /api/services/3).
Services are synced from Setmore (see APPOINTMENTS), and each sync
overwrites name, price, length and description, so edit them in Setmore.

PAYMENTS (hairpiece orders only)
POST /api/payments/create-intent          Start paying an order (customer)
                                          Body: {"order_id": 2}
                                          201: {"client_secret": "pi_..._secret_..."}
                                          404 order missing or not yours
                                          409 cancelled, no price, or already paid
                                          Calling it again for the same unpaid order
                                          returns the same client_secret (no double charge)
GET  /api/payments                        The customer's payments, newest first
                                          {"payments": [{payment_id, order_id, amount,
                                          payment_method, payment_type, status,
                                          charged_at, setmore_booking_id}]}
GET  /api/payments/<payment_id>           One payment; 404 if not theirs
GET  /api/admin/payments                  All payments, each with a "customer"
                                          {user_id, first_name, last_name, email} (admin)
                                          status=pending|succeeded|failed|refunded|cancelled
                                          ?from=2026-11-01&to=2026-11-30 (salon days)
GET  /api/admin/payments/<payment_id>     One payment with customer (admin)
POST /api/admin/payments/<payment_id>/refund
                                          Fully refund a card payment (admin), no body
                                          200: {"payment": {..., "status": "refunded"}}
                                          409 already refunded, not paid yet, or cash
                                          Refunds made in the Stripe dashboard also
                                          show up as "refunded" (through the webhook)


Payment status values: pending, succeeded, failed, refunded, cancelled.
charged_at is UTC; convert to local time for display.

HAIR CATALOG (public, no login)
GET  /api/catalog
     {"system_types": [{"key": "area", "label": "Hair loss area system", "price": 400.0},
                       {"key": "full", "label": "Full custom system", "price": 650.0}],
      "options": {"hair_type": ["Wavy", "Curly", "Straight"],
                  "base_type": ["Skin", "Lace"],
                  "skin_thickness": ["Thin (.02mm)", "Thick (.08mm)"],
                  "color": ["#1", "#2", "#3", "#4", "#5", "#6", "#7"],
                  "grey_percent": [0, 10, 20, 30, 40, 50, 60, 70, 80],
                  "density": ["Light", "Medium", "Heavy"],
                  "dimensions": ["6 x 8", "7 x 9", "8 x 10"]},
      "shipping_days": 10}
     Same values as data/hairOptions.js, with snake_case keys
     (hairType -> hair_type, greyPercent -> grey_percent, ...).
     Use this instead of hairOptions.js so prices live in one place.
     The full system price is a starting price; the real amount is set
     on the invoice after the consultation.

HAIRPIECE ORDERS
Order statuses: invoice_sent (waiting to be paid) -> pending (paid; the Stripe
webhook sets this) -> ordered -> received, or cancelled.
UI labels: invoice_sent = "Invoice sent" (customer side: "Invoice due"),
pending = "Pending", ordered = "Ordered", received = "Received".

POST /api/hairpiece-orders                Customer orders an area system online
     Body: {"specs": {"hair_type": "Wavy", "base_type": "Skin",
            "skin_thickness": "Thin (.02mm)", "color": "#3", "grey_percent": 20,
            "density": "Medium", "dimensions": "7 x 9"}}
     Every spec must be one of the GET /api/catalog options (snake_case keys).
     201: {"order": {order_id, order_type: "area", system_label, price: 400.0,
           order_status: "invoice_sent", hair_type, color_code, grey_percentage,
           density, skin_type, base_type, dimensions, placed_at, user_id}}
     400 lists each invalid spec in "details".
     Next: POST /api/payments/create-intent {"order_id"} to pay it.
GET  /api/hairpiece-orders                The customer's orders, newest first
GET  /api/hairpiece-orders/<order_id>     One order; 404 if not theirs
POST /api/hairpiece-orders/<order_id>/cancel
     Only while invoice_sent (unpaid); 409 after payment ("contact the salon").

GET  /api/hairpiece-orders/saved-system   My Hair System page, Customer Dashboard
     The customer's most recent PAID full system (from their consultation).
     {"saved_system": {order_id, system_type: "full", system_label,
       price, last_ordered, specs: {hair_type, base_type, skin_thickness,
       color, grey_percent, density, dimensions}}}
     or {"saved_system": null} if they don't have one yet.
     specs use the same keys as the catalog, so SpecList can show them.
POST /api/hairpiece-orders/reorder        "Re-order this system" button, no body
     201: {"order": {...}} a new full order with the same specs and price,
          status invoice_sent. Then pay it with create-intent.
     404 no saved system; 409 an earlier re-order is still unpaid (pay or
     cancel it first), or an option is no longer offered.

POST /api/admin/hairpiece-orders          Invoice after a consultation (admin)
     Body: {"user_id": 5, "system_type": "full" or "area",
            "specs": {...same keys...}, "price": 725}
     full: price required, at least 650; dimensions can be any text (custom).
     area: price is always 400 (any price sent is ignored).
     The customer then pays it like any order (create-intent).
GET  /api/admin/hairpiece-orders          All orders, each with "customer"
     {user_id, first_name, last_name, email} (admin)
     Optional: ?status=invoice_sent|pending|ordered|received|cancelled
PATCH /api/admin/hairpiece-orders/<order_id>/status   (admin)
     Body: {"status": "ordered"}    Allowed: pending -> ordered -> received.
     "cancelled" from invoice_sent or pending; 409 if the order is paid and
     not refunded (refund first: POST /api/admin/payments/<id>/refund).
     409 for any other jump (e.g. pending -> received).

REPORTS (admin)
Revenue counts only succeeded payments (refunded/cancelled are excluded).
Days follow the salon's clock (Houston), not UTC.

     {"days": [{"date": "2026-11-11", "label": "Wed", "value": 1245.0,
                "today": true}, ...oldest first],
      "total": 4520.0}
     Same shape as weeklySales in sampleData (label, value, today), so
     BarChart can use data.days directly. Admin Dashboard "Sales today" is

     {"customers": [{user_id, first_name, last_name, email, total_spent,
                     payment_count, last_payment_at}, ...highest first],

     Reports "Top customers" and "Average spend per customer".
     (For a customer's last appointment, use last_visit from

APPOINTMENTS
Bookings are made in Setmore. The sync copies them into our database;
the pages below read our copy.
Appointment shape:
  {setmore_booking_id, appointment_time, status,
   service: {service_id, service_name, duration_minutes, price} or null,
   customer: {user_id, first_name, last_name, email, phone}
          or, with no account on our site,
             {user_id: null, name, email, phone}}
status: booked | completed | no_show | cancelled
appointment_time: salon wall-clock time as stored from Setmore. If a
synced booking ever shows 6 hours off from Setmore, flip
APPOINTMENT_TIMES_ARE_UTC in frontend/src/api/format.js.

GET  /api/appointments                    The customer's own appointments (logged in)
GET  /api/appointments/<setmore_booking_id>  One of theirs; 404 otherwise
GET  /api/admin/appointments              All, oldest first (admin)
                                          ?start=2026-11-12&end=2026-11-18
GET  /api/admin/appointments/<setmore_booking_id>
POST /api/admin/appointments/<setmore_booking_id>/complete
POST /api/admin/appointments/<setmore_booking_id>/no-show
     Both only from "booked"; 409 if already completed or no-show.
     No-show adds 1 to the customer's no_show_count. No fee is charged.
POST /api/admin/appointments/sync?days=14 (admin)
     Syncs Setmore services first, then bookings for the next `days`.
     {"services": {...}, "appointments": {"created": [...],
      "updated": [...], "unchanged": [...], "skipped": [...]},
      "start_date", "end_date"}
     Needs SETMORE_REFRESH_TOKEN in backend/.env.

CHECKOUT PAGE FLOW (Stripe)
----------------------------------------------------------------------
Packages:  npm install @stripe/stripe-js @stripe/react-stripe-js
frontend/.env:  VITE_STRIPE_PUBLISHABLE_KEY=pk_test_...
                (Capstone sandbox publishable key; safe in the browser)

1. POST /api/payments/create-intent {"order_id"} -> client_secret.
2. Show Stripe's form:
     const stripePromise = loadStripe(import.meta.env.VITE_STRIPE_PUBLISHABLE_KEY);
     <Elements stripe={stripePromise} options={{ clientSecret }}>
       <PaymentElement />
     </Elements>
   (create stripePromise once, outside the component)
3. On Pay:
     const { error } = await stripe.confirmPayment({
       elements,
       redirect: 'if_required',
       confirmParams: { return_url: window.location.href },
     });
   If error, show error.message. Otherwise the payment went through.
4. The database is updated by Stripe's webhook a moment later, so
   GET /api/payments may still show "pending" for a second or two.
   Re-check after a short delay before showing it as paid.

Test cards: 4242 4242 4242 4242 (success), 4000 0000 0000 0002
(declined). Any future expiry, any CVC, any ZIP.
